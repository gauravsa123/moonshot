# LLM Wiki Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build a persistent, source-grounded Markdown wiki from the 53 documents currently under `raw/`, including a user-curated know-how skill profile for each of the 30 project/topic folders.

**Architecture:** Keep `raw/` immutable and Markdown pages under `wiki/` authoritative. Root `AGENTS.md` defines how the LLM maintains source, project, concept, and skill pages; a CSV inventory tracks each source and its ingestion status. Process one leaf project/topic folder at a time, stopping for know-how-skill confirmation between folders. Defer consolidated source/page quality review until the end. Each project separately records know-how needs, skills shown by source evidence, and user-reported contributions/outcomes. User reports have `user-reported` provenance, distinct from source evidence labels (`documented`, `inferred`, `unknown`). Graphs, charts, and portfolio content remain future derived views.

**Tech Stack:** Markdown, YAML frontmatter, CSV, local document reading through available LLM/tooling, and standard shell utilities. No packages or standalone graph database are required for this milestone.

Use path-qualified stable slugs for source pages to prevent same-named files from colliding. Use ordinary relative Markdown links. A skill page aggregates project links separately under “Projects needing this skill,” “Projects with user-reported use,” and “Projects showing this skill.”

## Task 2: Define the wiki and skill-profile contract

**Files:**
- Create: `AGENTS.md`
- Modify: `wiki/index.md`
- Modify: `wiki/log.md`

- [ ] **Step 1: Define page metadata and evidence labels**

In `AGENTS.md`, define frontmatter keys `id`, `type`, `title`, `aliases`, `related`, and `source_refs`. Restrict `type` to `project`, `source`, `concept`, or `skill`. For source-demonstrated skills and other factual claims, use an Evidence table with columns `Claim`, `Status`, and `Evidence`; allowed statuses are `documented`, `inferred`, and `unknown`. Documented/inferred claims link to source pages and page/slide locations when available.

- [ ] **Step 2: Define the project know-how and evidence lists**

Require every project page to have these sections:

```markdown
## Know-how needed

| Skill | Review status | Rationale |
|---|---|---|
| [Candidate skill](../skills/candidate-skill.md) | suggested | Why the project appears to need it |

## Skills shown by sources

| Skill | Evidence status | Evidence |
|---|---|---|
| [Skill](../skills/skill.md) | documented | [Source](../sources/source-page.md#slide-3) |

## User-reported contributions and outcomes

| Contribution or outcome | Status | Details |
|---|---|---|
| User-reported item | user-reported | User-confirmed description; not source-corroborated |
```

In `AGENTS.md`, define know-how review statuses as `suggested` and `user-confirmed`; remove rejected suggestions instead of counting them. Users may add, remove, rename, or regroup suggestions. Clearly state that a suggested or confirmed project requirement is not evidence that the user personally demonstrated the skill. Source-demonstrated skills use only the evidence labels `documented`, `inferred`, or `unknown`. User-confirmed personal contributions/outcomes use the separate provenance/status `user-reported`; do not relabel them as source evidence without corroboration.

- [ ] **Step 3: Define skill-page aggregation**

Require each canonical skill page to define the skill briefly, list aliases and parent/related skills, and link projects under distinct “Projects needing this skill,” “Projects with user-reported use,” and “Projects showing this skill” headings. The middle heading records user-reported use, not source evidence; only source-supported claims belong under “Projects showing this skill.” Merge aliases only when the user agrees that the terms refer to the same skill; never silently collapse distinct capabilities.

- [ ] **Step 4: Specify ingestion and review behavior**

In `AGENTS.md`, instruct the LLM to process one leaf topic folder at a time; record every file as `processed`, `needs review`, or `blocked` with a reason; preserve `raw/`; and update the inventory, source/project/skill/concept pages, index, and log together. After proposing project know-how skills, ask the user to confirm, edit, or reject them before marking any as user-confirmed or using them as canonical taxonomy entries. Keep user-reported contributions/outcomes distinct and use `user-reported` provenance/status. Present a folder report and wait for user review before starting the next folder.

- [ ] **Step 5: Specify query and health-check behavior**

Document that wiki queries start at `wiki/index.md`, answers cite the wiki/source pages used, and answers are filed only when requested. New files follow the same incremental workflow. Health checks report broken links/source references, unindexed or orphan pages, unsupported claims, conflicts, stale conclusions, and unreviewed inferences without silently rewriting disputed content.
